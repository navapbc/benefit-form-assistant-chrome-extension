# Developer Mode Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a Developer mode switch in the side panel, off by default, that keeps experimental features out of the default app in both the panel and the service worker.

**Architecture:** One shared module (`shared/developer-mode.mjs`) owns the storage key, a fail-closed reader, and the single list of experimental dispatcher actions, screens and service-worker message types. The service worker reads storage itself before routing any experimental message. The panel loads the setting before its first render, refuses experimental actions in its one dispatcher, and hides experimental controls in its views.

**Tech Stack:** Plain ES modules (no build step), Chrome MV3 `chrome.storage.local`, `node --test` with `.cjs` tests that `require()` the `.mjs` files.

**Spec:** `docs/superpowers/specs/2026-10-21-developer-mode-design.md`

## Global Constraints

- Setting is stored in `chrome.storage.local` under the key `nava:developer-mode`; only the value `true` means on. Missing, `false`, any other value, or an unreadable store means **off**.
- Default is **off**, including for existing installs.
- With the switch on, behavior is exactly what it is today.
- No deleting of experimental code; stored experimental state is ignored when off, never removed or overwritten.
- No top-level `await`, no import cycles, no `Nava*` global reads: `npm run check:modules` enforces this.
- The service worker must read the setting from storage itself, never from a message.
- Gate by individual action name, not by whole action table.
- Core stays: Gemini Nano, details and sample clients, document upload, participant directory, one application at a time, questions, review, activity log export, the human checkpoints.
- CI must stay green: `npm run lint`, `typecheck`, `check`, `check:package`, `check:modules`, `check:vendor`, `check:docs`, `npm test`, `npm run eval:extraction`. Do not commit files regenerated by `eval:extraction` (`evaluation/latest-report.*`).
- Commit trailer: `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`.

## Decisions that differ from or sharpen the spec

- **Connector router is split.** `OPEN_PROGRAMS` (core: opens the selected application tabs) and `GET_CONNECTOR_STATUS` (read-only status the panel reads at start-up) are routed by the connector client but must keep working. Only these message types are refused when off: `NAVA_CAPTCHA_COMMAND`, `DISCOVER_CONNECTOR`, `SAVE_CONNECTOR`, `RESET_CONNECTOR`, `LOOKUP_RECORD`, `LIST_RECERTIFICATIONS`.
- **A refused message answers `{ ok: false, error: 'Developer mode is off.' }`**, not silence. The setting is read asynchronously, so the router must keep the response channel open; the panel already treats `!response?.ok` as an error. (The spec said silent `false` for non-CAPTCHA types; this is the practical form of it.)
- **Switching the mode is blocked while any application run is active**, the same rule as changing the model runtime (`activeRunCount()`), so no running experiment is cut off mid-step by the panel. The service worker also cancels CAPTCHA attempts when the setting turns off, as a second guard.
- **Preview mode** (`?preview=1`) keeps the setting in page memory like the welcome flag, default off.

## Review Focus

- Corrupt or non-boolean stored value (`"true"`, `1`, `null`, `{}`): must read as off. Pinned in Task 1.
- Storage read throws or is unavailable in the service worker: experimental messages are refused, core messages still work. Pinned in Task 2.
- Switch turned off while a CAPTCHA scope is live or stored experimental state exists (agent provider `jev`, a stored connector): nothing experimental runs, nothing is deleted, turning it back on restores it. Pinned in Tasks 2 and 5.
- A caseworker mid-session on an experimental screen (`connector`, `recertifications`, `handoff`, `record`) when the mode turns off: the panel lands on the start screen, not a blank page. Pinned in Task 3.
- With the switch off a running application can still be stopped, and a CAPTCHA checkpoint can still be finished by hand with "resume". Pinned in Task 4. If no stop path exists besides `pause`, keep `pause` out of the experimental list and tell the user.

### Task 1: Shared module

**Files:**
- Create: `shared/developer-mode.mjs`
- Test: `tests/developer-mode.test.cjs`

**Interfaces:**
- Produces:
  - `STORAGE_KEY: 'nava:developer-mode'`
  - `readDeveloperMode(storage: { get(key): Promise<object> }): Promise<boolean>`, never throws
  - `writeDeveloperMode(storage: { set(obj): Promise<void> }, enabled: boolean): Promise<void>`
  - `EXPERIMENTAL_ACTIONS: ReadonlySet<string>`: dispatcher click action names, submit form ids and change-handler element ids
  - `EXPERIMENTAL_VIEWS: ReadonlySet<string>`: `state.view` values
  - `EXPERIMENTAL_MESSAGE_TYPES: ReadonlySet<string>`
  - `isExperimentalAction(name): boolean`, `isExperimentalView(view): boolean`, `isExperimentalMessage(type): boolean`
  - `DEVELOPER_MODE_OFF_MESSAGE: 'Developer mode is off.'`

- [ ] **Step 1: Write failing tests** in `tests/developer-mode.test.cjs`:
  - `reads only true as on`: for stored values `true` → `true`; `false`, `"true"`, `1`, `null`, `{}`, and a missing key → `false`.
  - `a throwing or missing store reads as off`: `get` rejects; `storage` undefined → `false`.
  - `write stores a strict boolean`: `writeDeveloperMode(s, 1)` stores `true`; `writeDeveloperMode(s, 0)` stores `false`; key is `nava:developer-mode`.
  - `the experimental lists contain exactly the spec's items`: click actions include `try-captcha`, `open-handoff`, `accept-handoff`, `pause`, `save-planner`, `disconnect-planner`, `client-link`, `choose-id`, `configure-connector`, `back-providers`, `select-provider`, `back-connector`, `local-connector-settings`, `reset-connector`, `back-record-id`, `confirm-connector-record`, `open-recertifications`, `back-recertifications`, `review-recertification`, `draft-recertification-outreach`, `complete-recertification-outreach`, `prepare-recertification`; submit ids include `record-form`, `connector-form`, `connector-mapping-form`, `recertification-intake-form`, `handoff-form`; change ids include `connector-provider`. Core names are **not** in the set: `fill`, `run`, `answer`, `review`, `resume-human-checkpoint`, `start-over`, `add-application`, `export-audit`, `directory-pick`, `details-form`, `document-form`, `program-form`, `model-provider-form`.
  - `message types`: set equals exactly `NAVA_CAPTCHA_COMMAND`, `DISCOVER_CONNECTOR`, `SAVE_CONNECTOR`, `RESET_CONNECTOR`, `LOOKUP_RECORD`, `LIST_RECERTIFICATIONS`; `OPEN_PROGRAMS` and `GET_CONNECTOR_STATUS` are not in it.
  - `views`: set contains `connector`, `providers`, `connector-mapping`, `record-review`, `record`, `recertifications`, `recertification-detail`, `handoff`; does not contain `choice`, `details`, `welcome`, `document`, `document-review`, `programs`, `dashboard`, `questions`, `review`.

### Task 2: Service worker gate

**Files:**

- Test: `tests/captcha-service.test.cjs`, plus the existing test file that builds the service worker with a fake `chrome` (find it with `grep -ln "routeMessage\|onMessage" tests/*.cjs`; mirror its setup)

**Interfaces:**
- Consumes: `readDeveloperMode`, `isExperimentalMessage`, `DEVELOPER_MODE_OFF_MESSAGE`, `STORAGE_KEY` from Task 1.
- Produces: `captchaService.cancelAll(): void` (revokes every live scope, same effect as `cancelApplications` for all ids).

- [ ] **Step 1: Write failing tests:**
  - captcha-service: `cancelAll revokes every live scope` (two scopes for different applications; after `cancelAll()` a later `check` on either throws "authorization expired or was canceled").
  - service worker, with developer mode **off** in fake `chrome.storage.local`: sending `NAVA_CAPTCHA_COMMAND`, `DISCOVER_CONNECTOR`, `SAVE_CONNECTOR`, `RESET_CONNECTOR`, `LOOKUP_RECORD`, `LIST_RECERTIFICATIONS` from the side-panel sender each calls `sendResponse` with `{ ok: false, error: 'Developer mode is off.' }`, and the router returns `true`. `OPEN_PROGRAMS` and `GET_CONNECTOR_STATUS` still reach their handlers.
  - `storage.get` rejecting counts as off (same refusals).
  - With the setting `true`, `LOOKUP_RECORD` reaches its handler as before.
  - `turning the setting off cancels live CAPTCHA scopes`: fire the fake `chrome.storage.onChanged` listener with `{ 'nava:developer-mode': { newValue: false } }` in area `local`; assert `cancelAll` ran. A change to `true`, to another key, or in area `session` does nothing.
- [ ] **Step 2: Run** the new tests. Expected: FAIL.
- [ ] **Step 3: Implement.** `cancelAll` iterates `scopes.values()` calling `revoke`. In `routeMessage`, before any router: if `isExperimentalMessage(message?.type)`, read `readDeveloperMode(chrome.storage.local)`; when on, call the original routing and forward its result to the same `sendResponse`; when off, `sendResponse({ ok: false, error })`; return `true` either way. Register `chrome.storage.onChanged` once: when area is `local`, the key changed, and `newValue !== true`, call `captchaService.cancelAll()`.
- [ ] **Step 4: Run** tests, `npm run check:modules`, `npm run lint`. Expected: PASS.
