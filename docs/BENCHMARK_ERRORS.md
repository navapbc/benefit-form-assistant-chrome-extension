# Benchmark errors and reproduction details

This catalog explains what failed, what was expected, and which evidence supports it. It includes application errors, conservative deferrals and harness failures separately. A planning pass, persisted write or accepted CAPTCHA is not a correctly completed application. All fixtures use fictional records; application Submit stays untouched.

The [individual result tables](../evaluation/results/README.md) retain timings, usage and price scenarios. The [CAPTCHA ledger](CAPTCHA_RUN_METRICS.md) retains successful attempts, rejected answers, timeouts, startup failures and unknown costs. Exact historical exceptions were not always retained publicly; missing diagnostic detail is identified below instead of reconstructed.

### Reproduce F01 without private data

1. Load v0.14.0 in Chrome and use an invented participant with a complete residential address, for example `100 Test Way, Apt 2, Riverside, CA 92501`.
2. Open the [Riverside WIC form](https://www.ruhealth.org/appointments/apply-4-wic-form), choose **Analyze this form**, and continue with Nano, Jev or the CLI planner.
3. Read the Home Address box before any manual repair. The observed value is `100 Test Way, Apt 2`; city, state and ZIP are absent even though required-field HTML validation succeeds.
4. Export the activity log and independently compare all 17 applicable semantic answers with the source. A verified write is insufficient: the address answer is incomplete.

The [WIC site adapter](../shared/site-adapters.js) maps `edit-home-address` to `addressLine1`. The [form engine](../shared/form-engine.js) combines street and unit when there is no unit field; that branch does not compose the remaining address components. This code evidence explains the shared transformation defect. Changing the model alone does not validate a fix. The deterministic local playbook used a different address composer and scored 17/17 on the frozen fixture; live adoption is not yet validated.

## What each new run must retain

- **Identity:** extension commit/version; site and record hash; form runtime; requested and provider-reported model; reasoning effort or explicitly unknown; image runtime and actuator origin.
- **Speed:** timestamped start, each scan, fill/readback, terminal checkpoint, CAPTCHA start/end, final-review observation. Report time to failure as well as time to success. Keep operator wait separate from engine wall time and concurrent model-duration sums.
- **Quality:** correct, incorrect, missing and not-applicable semantic answers; exact failing field/question; expected vs observed behavior; false gaps; assistance count/type; HTML validity and extension readback as separate checks.
- **Usage/cost:** prompt count; input/output/cached/reasoning tokens when available; Nano context units separately; pricing date/source/formula; direct API charges, list-price scenario and unknown billed/operating costs separately.
- **CAPTCHA:** whether reached/attempted; checkbox-only vs image session; rounds and rejected answers; visible provider acceptance; unsupported/refusal/timeout/executor/observation reasons. A checkbox with no image call is a shared actuator result, not evidence of that model's image-solving skill.

An unavailable runtime, an unattempted CAPTCHA, and a rejected challenge are different rows. No success rate is computed from only the successful runs. Two repeats and one fictional record are exploratory evidence, not reliability estimates.
